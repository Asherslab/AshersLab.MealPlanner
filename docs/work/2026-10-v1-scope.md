# Version 1 scope

The agreed design for the first usable version, and the order to build it in. Agreed with the owner
in a design discussion on 2026-10-20, before any code existed; skipping and the pantry were added
with the owner on 2026-10-21. Read this first; the other `docs/work/`
docs expand individual sections and are linked where they apply.

## Who it is for, and what it replaces

The household's main planner (not a developer) runs a meal plan in a Google Sheet today: a 4-week
rotation of breakfast / snack / lunch / snack / dinner, a list of meal ideas with their ingredients
and how many meals a batch makes ("4x Spaghetti bolognese (spaghetti, beef, bolognese, grated
cheese…)"), and a shopping-category list of every ingredient with an empty price column. A copy is at
`private/Grocery budget.xlsx`.

The app replaces that sheet and adds what a sheet cannot do well: what each meal and each week
actually costs, a shopping list per store, and serves tracked as leftovers are eaten.

Groceries come from two stores:

- **Woolworths** — online orders, roughly weekly, invoices downloadable as text PDFs.
- **Costco** — in-warehouse, roughly weekly, receipts exported from the Costco app as **image-only**
  PDFs. Several staples (beef mince, eggs, fruit, bread) come mainly from here, so a Woolworths-only
  price would be wrong for most beef meals.

There are three people: two adults and a toddler. The toddler's meals are mostly separate; the
planner handles them by planning slots per person. **No portion-size arithmetic** — a serve is a
serve.

It is used on both phone and desktop. Mobile layout is not an afterthought: the shopping list is used
one-handed in a shop with poor reception.

## Decisions already made

These were settled in the design discussion. Do not reopen them without a reason the discussion did
not have.

| Area | Decision |
|---|---|
| Front end | Blazor **WebAssembly** + MudBlazor. Responsive: desktop and phone. |
| API | Code-first gRPC (`protobuf-net.Grpc`), **gRPC-Web** from the browser. Same conventions as the GSBC repos. |
| Data | **Offline-first.** SQLite in the browser + an op log; server SQLite is the master; the API syncs and resolves conflicts. See [offline sync](../modules/sync/offline-sync.md). |
| Server DB | SQLite via EF Core (not Postgres) — runs on a Raspberry Pi. Keep it EF-portable so Postgres stays a config change. |
| Hosting | **Home Assistant add-on** (Raspberry Pi, HA OS, aarch64) via ingress, **and** standalone container (k8s / Docker). One image. See [deployment](../modules/infrastructure/deployment.md). |
| Images | Built by GitHub Actions, pushed to **GHCR** (not Docker Hub). Multi-arch amd64 + arm64. |
| Storage | HA: `/data` (in HA backups). k8s: PVC. Optional Litestream replication of the SQLite file to S3. |
| Receipts | **Parsed and discarded.** Only the extracted data is stored. The file is shown during review, then dropped. |
| Receipt parsing | **In the browser.** Woolworths: PDF text extraction. Costco: OCR (tesseract.js) — "if reliable enough"; server-side Tesseract is the fallback. No iOS-only paths. See [receipts](../modules/receipts/receipts.md). |
| Quantities | **Grams, millilitres, or "each"** per ingredient. Not fractions of a pack. |
| People | Plan slots belong to the household or to chosen people. No portion scaling. |
| Serves | Tracked against the calendar: cooking a batch makes serves, leftovers slots consume them. |
| Skipping | A planned entry can be **skipped** and replanned later. A skipped entry eats nothing, cooks nothing and costs nothing. Added 2026-10-21. |
| Pantry | **Estimated stock on hand per ingredient**: up when bought, down when cooked, corrected by hand. Without it the shopping list assumes an empty kitchen every week. Expiry dates are later. Added 2026-10-21. |
| Shopping list | Generated from the calendar **less pantry stock**, split by store, with free-form extra items (household, unplanned). |
| Budget | Actual Budget, **one "Groceries" category**, read through `actual-http-api`. **Version 2.** |
| Live prices | Woolworths' undocumented web API, server-side. **Version 2** — receipts come first. |
| Existing data | The planner's spreadsheet is imported as editable drafts. |

## Domain model

Names are a starting point, not a contract. Money is integer cents. Quantities are `decimal` in the
ingredient's base unit.

### Catalogue

- **Store** — Woolworths, Costco, plus user-added ("Other", the butcher). Seeded.
- **Ingredient** — the generic thing a recipe needs: "beef mince", "grated cheese".
  - `BaseUnit`: `Gram | Millilitre | Each`. One per ingredient; no conversions between them.
  - `Category`: the shopping categories from the planner's sheet — Meat, Dairy, Fruit, Vegetables,
    Carbs/sides, Pantry, Fridge, Freezer, Household. Drives shopping-list grouping. Editable list.
  - `UsualStoreId` — where it goes on the shopping list.
  - `IsStaple` — pantry items (soy sauce, oil, seasonings) used in small amounts. Costed by quantity
    like anything else, but left off the generated shopping list unless marked "running low".
- **Product** — a thing a store actually sells: "Costco beef mince 8×250g".
  - `StoreId`, `Name`, `StoreCode` (Woolworths stockcode / Costco item number — nullable),
    `PackQuantity` in the linked ingredient's base unit (2000 g), `IngredientId` (nullable — household
    items and ignored lines have none).
  - `Aliases` — every raw receipt description that has been matched to it. This is what makes the
    second receipt import automatic.
  - Many products per ingredient (one per store, sometimes more).
- **PriceObservation** — `ProductId`, `PriceCents` for one pack, `ObservedOn`, `Source`
  (`Manual | Receipt | Live`), optional `ReceiptLineId`. For variable-weight meat also the per-kg
  price. Append-only: the history is the point.

### Meals

- **Meal** — name, group (Beef / Chicken & egg / Fish / Other / Individual / Side / Snack — the
  planner's sheet columns; editable), `ServesPerBatch` (the sheet's "4x"), notes.
  - `Kind`: `Cooked` (has ingredients, makes a batch), `Simple` (single serve, costed by
    ingredients, no batch — "Bagels, scrambled eggs + toast"), `Leftovers` (consumes a batch),
    `NoCost` ("Family dinner", eating at someone else's), `FixedCost` (takeaway, with a typed
    amount).
- **MealIngredient** — `MealId`, `IngredientId`, `Quantity` (nullable — "not entered yet" is a real
  state the import produces), note.

### Planning

- **Person** — name, colour. Not seeded: the planner adds the household in the app (names are never in the
  repo). Amended 2026-10-21 at slice 8.
- **Slot** — Breakfast, Snack, Lunch, Snack, Dinner; ordered, editable.
- **PlanTemplate** — name, `WeekCount` (the existing one is 4).
  - **TemplateEntry** — week number, weekday, slot, people (all, or a subset), and **one or more
    meal choices**. The sheet has cells like "Leftovers/mi goreng/pizza": that is three choices, not
    one meal. A single choice is the common case.
- **CalendarEntry** — a real date, slot, people, the meal actually planned (one, chosen from the
  template's choices or overridden), and for leftovers which batch it eats from.
  - Generated by applying a template from a start date over a range; each generated entry remembers
    its template entry so re-applying does not clobber manual overrides.
  - `Status`: `Planned | Skipped`. An entry whose date has passed and is still `Planned` counts as
    eaten — nobody ticks off every meal. **Skipping** ("we didn't have it") is the one thing to record.
    A skipped entry can be **replanned**: moved to another date and slot, or left on a "to replan"
    list to drop back in later. Re-applying the template does not resurrect a skipped entry (it
    remembers its template entry, as above).
  - Skipping a `Cooked` entry means the batch was never cooked: no serves made, nothing drawn from
    the pantry, and every leftovers entry linked to that batch is flagged as having nothing to eat —
    never silently left pointing at it. Skipping a `Leftovers` entry returns its serve to the batch.
- **Batch** — created when a `Cooked` calendar entry is planned: `MealId`, cook date, `ServesMade`
  (defaults to the meal's `ServesPerBatch`, editable). Serves remaining = made − serves consumed by
  calendar entries linked to it (people count × 1 each). Surface: "3 serves left after Thursday",
  "Saturday's leftovers has nothing to eat", "2 serves will go uneaten".

### Pantry

Added 2026-10-21. The pack-rounding spare below ("1 pack, 1.25 kg spare") is pantry stock; the
original design computed it and then forgot it, so every week's list assumed an empty kitchen. Half a
jar of mayo bought this month should be used, and not re-bought, next month.

- **StockMovement** — an append-only ledger per ingredient, in its base unit: `IngredientId`,
  `Quantity` (signed), `OccurredOn`, `Reason`:
  - `Bought` — a shopping-list line ticked `Bought` (the whole packs, not the amount needed), or a
    matched receipt line. A receipt must reconcile with the `Bought` ticks it covers, not add the
    same mince twice; the exact rule is settled in the receipt slice.
  - `Cooked` — a `Cooked` or `Simple` calendar entry on its date, by the meal's ingredient
    quantities. Skipped entries draw nothing. Projected for future dates, actual for past ones.
  - `Adjusted` — a correction by hand: "we're out", "about half left", "threw it out". The estimate
    **will** drift (recipes are approximate, nobody weighs the mayo), so correcting must be one or two
    taps, and a stocktake sets the level rather than adding to it.
- **Stock on hand** = the sum of movements up to a date. Never below zero — a draw-down past zero is
  a sign the estimate drifted, shown as "probably out", not as negative stock.
- **Staples** (oil, soy sauce, spices) are not drawn down gram by gram. Their stock is a hand-set
  state — `Have | Running low | Out` — which is what the existing "running low" flag becomes.
- Costing is by quantity, so a part-used pack is already costed fairly; see the two cost views
  below.
- **Expiry is later** (see Out of version 1). It needs stock per purchase lot instead of one total,
  and version 1 does not depend on it.

### Shopping

- **ShoppingList** — a date range. Generated lines are computed, not stored: for every calendar
  entry in range, the meal's ingredient quantities (a batch counts once, on its cook date), summed per
  ingredient, **less the pantry stock projected for the list's start date**, grouped by usual store,
  then by category.
  - "Need 300 g mayo, have about 250 g" → buy 1. Covered entirely by stock → shown as "in the
    pantry" (so it can be checked), not as a line to buy.
  - Pack rounding: need 750 g of mince, product pack is 2000 g → "1 pack (1.25 kg spare)". The spare
    goes into the pantry when the pack is ticked `Bought`.
  - Staples are omitted unless `Running low` or `Out`.
- **ShoppingListItem** (stored) — ticks (`Have it` / `Bought`) against generated lines, plus
  free-form extra items with an optional store and price. These sync, so ticking on the phone shows
  on the desktop. `Bought` writes a `Bought` stock movement; `Have it` on a line the pantry thought
  was empty writes an `Adjusted` one.

### Receipts

- **Receipt** — store, date, the store's order/receipt number (dedupe key — importing the same
  receipt twice is refused, naming the earlier import), subtotal, fees (bag fee), total, paid,
  refund.
- **ReceiptLine** — raw description, store code, quantity, unit price, line amount, weight (variable
  meat), discount applied, the store's category, `ProductId` once matched, and `Kind`
  (`Food | Household | Fee | Ignored`).
- **The file itself is never stored.**

### Budget (version 2)

- **BudgetMonth** — month, budgeted, spent, balance for the Groceries category, fetched-at time.
  Written by the server, synced down like any other data.

## How a cost is computed

Pure functions, unit-tested, in a project both server and client reference (the browser computes
costs offline from its local data).

1. **Ingredient unit price** — from the ingredient's product at its usual store, latest observation
   of any source. Falls back to the cheapest-per-unit product at any store with an observation. None
   → unpriced.
2. **Meal batch cost** = Σ `Quantity × unit price` over its ingredients. Any ingredient with no
   quantity or no price makes the cost **incomplete**: show "from $X" and how many are missing,
   never a silently low number.
3. **Per serve** = batch cost ÷ `ServesPerBatch`.
4. **Calendar cost**, two views — they answer different questions:
   - **Spend** — what the week's shop costs: the **whole packs** the week's shopping list buys
     after pantry stock (Shopping, below), plus fixed-cost meals. Leftovers and pantry stock cost
     nothing here (already bought). This is the one compared with the budget. (Before the pantry was
     added this was "batches by cook date", which charged a recipe's quantities and never the pack
     actually bought.)
   - **Eaten** — what the week's food was worth: serves eaten × per-serve cost, by quantity. Half a
     jar of mayo costs half a jar in the month it is eaten. Skipped entries count in neither view.
5. **Month** — sum of spend over the month, against Actual's budgeted/spent (version 2).

## Importing the existing spreadsheet

An in-app import (upload the `.xlsx`, or the Google Sheets export of it) that creates **drafts** the
planner reviews. It is a one-off migration but built as a feature, because the sheet is personal data
that must not be committed as seed data. Parse in the browser.

What the sheet holds, and what each part becomes:

| Sheet region | Becomes | Notes |
|---|---|---|
| Sheet1 rows "WEEK 1"…"WEEK 4", then one row per slot, columns Mon–Sun | A 4-week `PlanTemplate` | Slot labels have suffixes ("Lunch (sandwich for …)") — map by the leading word. |
| "MEAL IDEAS" block: one column per meal group, cells like `4x Risoni (risoni, beef, bolognese, …)` | `Meal`s with `ServesPerBatch` and `MealIngredient`s with no quantity | The `Nx` prefix is optional, sometimes `8?x`. Parentheses are sometimes unclosed. Cells with no parentheses are `Simple` meals or sides. |
| "COSTS" block: one column per shopping category, one ingredient per cell | `Ingredient`s with `Category` | The Non-food column becomes household products, not ingredients. One cell has a price in it ("… 59.99/148") — take it as a manual price observation. |
| Sheet2: a flat ingredient list | Merged into the ingredients above | Has duplicates and case differences. |

Known mismatches to resolve during import, not silently:

- The plan names a meal slightly differently from the meal ideas list (a letter transposition in one
  case). Fuzzy-match and ask.
- Plan cells combining alternatives with `/` → multiple choices.
- "Family dinner" → `NoCost`; "Leftovers" → `Leftovers`.
- Plan cells that combine several simple items ("Crackers, cheese, ham") → one `Simple` meal each,
  created on first sight, reused after.
- Units are unknown for every imported ingredient. Guess (`Each` for bagels, eggs, wraps, tortillas,
  avocados, bananas; `Gram` for meat, cheese, rice, pasta; `Millilitre` for sauces, milk, oil), and
  mark every guess for review.

## Out of version 1

Deliberately later, in roughly this order:

1. **Actual Budget** — Groceries budgeted / spent / remaining for the month next to planned spend.
   Through `actual-http-api` (bundled in the add-on, a sidecar in k8s). Its bank transactions also
   let a receipt be checked off against the card charge, and show a shop with no imported receipt.
2. **Woolworths live prices** — server-side refresh of every product with a Woolworths stockcode,
   weekly (specials change on Wednesdays). Price history then shows "beef on special this week".
3. **Planned vs actual** — a week's planned spend against its imported receipts.
4. **Pantry expiry dates** — optional best-before per purchase, which means stock per lot (first
   in, first out) instead of one total per ingredient. Then "use the spinach before Thursday", and
   suggesting meals that use what is about to expire. Added 2026-10-21.
5. **HACS integration** — sensors in Home Assistant ("budget remaining", "tonight's dinner",
   "casserole serves left") and a dashboard card. Optional; the add-on works without it.

Not planned at all: Coles, other stores' live prices, nutrition, recipe instructions.

## Build order

Each numbered item is one or more vertical slices per the root `AGENTS.md`. Slices 0–3 are the
foundation and are proven before any feature UI: they carry the riskiest unknowns, and every later
slice depends on them.

0. **Scaffold.** Solution `AshersLab.MealPlanner.sln`; projects modelled on GSBC.Accounting minus YARP
   and the migrations worker (see the [deployment design](../archive/2026-10-deployment.md) for why); AppHost for local
   dev; ports picked and recorded in `.claude/app-local.md`; `./update-sln-docs.sh` run.
1. **Browser SQLite that survives a reload** — in Chrome desktop and Safari on iOS. Settles
   [sqlite-in-the-browser](../open-questions/sqlite-in-the-browser.md).
2. **Op log, push and pull, for one entity** (Ingredient: create and rename), two browser profiles
   converging, and an offline edit syncing on reconnect.
3. **The image, on the Pi.** CI builds the arm64 image to GHCR; the add-on installs in Home
   Assistant; the WASM app loads through ingress, gRPC-Web calls succeed, and the HA user is known
   to the server. Settles [home-assistant-ingress](../open-questions/home-assistant-ingress.md).
   Doing this before the features means a packaging dead end costs one slice, not a rewrite.
4. Ingredients, stores, categories — full CRUD. Landed 2026-10-21: [the catalogue](../modules/catalogue/catalogue.md).
5. Products and manual prices. Landed 2026-10-21: [products and prices](../modules/catalogue/products-and-prices.md),
   including step 1 of "How a cost is computed" (two products at the usual store: the cheaper per unit). Receipt
   aliases are their own rows, written by slice 12, not a field of the product.
6. Meals and their ingredients, with batch and per-serve cost. Landed 2026-10-21: [meals](../modules/meals/meals.md),
   including steps 2 and 3 of "How a cost is computed". Meal groups are an editable, ordered, seeded list like the
   shopping categories; a fixed-cost meal's amount is for the whole thing, shared over the serves it feeds.
7. Spreadsheet import. Landed 2026-10-21, removed 2026-10-23: [spreadsheet import](../archive/2026-10-spreadsheet-import.md) - categories,
   ingredients (units marked as guesses), meal groups, meals and their lines, household products and every price the
   sheet holds; running it again adds only what is new (a later download's prices). The 4-week plan is parsed
   (`ParsedSheet.Plan`) but not imported: slice 8 imports it with the templates, including the plan cells' simple
   meals ("Crackers, cheese, ham") and the fuzzy match of plan names to meals.
8. People, slots, plan templates. Landed 2026-10-21: [plan templates](../modules/planning/plan-templates.md) and the
   plan part of [spreadsheet import](../archive/2026-10-spreadsheet-import.md#the-plan) (removed since). A template entry is one thing
   eaten (one meal from its choices), so "Crackers, cheese, ham" is three entries; who eats it is one field, null for
   everyone; the imported plan has a fixed id and is imported once.
9. Calendar: apply a template, override an entry, choose between alternatives, skip and replan
   an entry. Landed 2026-10-22: [the calendar](../modules/planning/calendar.md). A plan remembers the Monday its week 1
   began (`StartsOn`); entries a plan makes have ids derived from their template entry and date, and their creates carry
   only what never changes, so applying is safe to repeat and to run on two phones at once. An untouched entry follows
   the plan; a changed one keeps its own meal and people. "Left on a to-replan list" is every skipped entry; removing
   one is a delete. What a skip does to batches is slice 10's.
10. Batches and serves, including what a skip does to them. Landed 2026-10-22: [batches and serves](../modules/planning/batches-and-serves.md).
    A batch is the cooked calendar entry itself (no row of its own); serves are counted from the calendar, never stored,
    so no counter op was needed. `ServesMade` and `EatsFrom` are fields of the entry. The cooking night's eaters eat from
    the batch too. Leftovers eat "whatever is left" oldest first, within a week. The 2026-10-22 review fixes also made a
    change of a plan's start or week count apply from a date on (`RotationPhases`), so past serves never move.
11. Shopping list, including ticks and extra items.
    - **Pantry** comes first, as its own slices before the list: the stock ledger, hand corrections
      and staple states, drawn down by cooked entries. Then the shopping list subtracts stock, and
      `Bought` ticks add to it. Receipts (12, 13) then add to stock too. Numbered under 11 rather
      than renumbering, because other docs refer to slices 12 and 13 by number.
    - Pantry landed 2026-10-22: [the pantry](../modules/pantry/pantry.md). What cooked and simple meals use is read from
      the calendar, never stored as `Cooked` movements, so a skip or a plan change moves the stock with no op and nothing
      can be drawn twice; the stored reasons are `Bought`, `Adjusted` and `Counted` (a stocktake, which sets the level). A
      day's hand changes come before its meals. The shopping list reads `PantryBook.LoadAsync(db, start, end).At(i, start)`.
    - Shopping list landed 2026-10-22: [the shopping list](../modules/shopping/shopping-list.md), including step 4 of "How a
      cost is computed" (Spend and Eaten, on the list and under the calendar's week). A list's and a tick's ids are derived
      (dates; list and ingredient), so two phones converge. The list reads the pantry **without its own ticks** (each
      movement a tick writes names it, `StockMovement.ShoppingItemId`), so a line ticked bought stays a line to buy; a tick
      undoes the line's last one first. Pack choice is the cheapest for the packs needed at the usual store, not the
      cheapest per gram. A fixed-cost meal's spend is a serve per eater.
12. Woolworths receipt import and product matching. Landed 2026-10-22: [receipts](../modules/receipts/receipts.md). The PDF's
    text is read in the browser by a vendored pdf.js and parsed by position; a receipt that does not add up is refused. Every
    id is derived from the store and order number, so a second import is one lookup and two phones importing one invoice
    converge. Matching is the store's code, then an alias (its own row, one per description), then suggestions the planner
    confirms. **The reconciliation rule:** a receipt's purchase replaces the shopping-list tick of the same ingredient
    nearest in date (a week before to two days after) - its movement names the tick (`CoversItemId`), and the tick's
    movements stop counting everywhere; the planner can turn it off. Staples get prices but no movements. The same review
    fixes made stock follow a tick rather than its rows (two phones ticking one line bought put one pack in the pantry).
13. Costco receipt import (OCR). Landed 2026-10-22: [receipts](../modules/receipts/receipts.md). The open question is settled
    **in the browser**: tesseract.js, vendored, reads the receipt's one bitmap (not its two pages) with every item number,
    name, price and total exact on both real receipts; its only misreads are in the amount column (the GST flag run in, a
    lost decimal point), which the reader undoes by rule, and both real receipts add up with no correction. A receipt that
    does not add up is corrected in the review, beside the strip of the picture each line came from. A receipt's store
    is the reader's, never the planner's. Item numbers become product codes, so the next receipt
    matches by code. A discount's price is not recorded: the shelf price is.
14. Standalone deployment. Landed 2026-10-22: [deployment](../modules/infrastructure/deployment.md). A Helm chart
    (`Charts/mealplanner`): one replica, Recreate, a kept PVC, non-root, probes ahead of the sign-in gate, Pi-sized limits,
    optional NetworkPolicy and Litestream (sidecar, plus a restore on an empty PVC). Auth is a sign-in proxy's user header
    believed only from the proxy's addresses; **the image with no auth configured refuses to start** unless told
    `Auth:Mode=None`. No built-in password. Not yet run against a real cluster - the owner's steps are in the doc.

15. Acceptance walk-through. Driven 2026-10-22 on a phone-sized screen from an empty database:
    [the v1 acceptance handover](2026-10-v1-acceptance.md). Every step below works; seven small gaps were fixed on the way
    (a new ingredient from the meal, a new meal from the calendar, "4 unpriced" rather than "from $0.00", a real home page,
    and others). What remains is the owner's: the iPhone, the add-on on the Pi with a real backup and restore, wiping the
    test data, and the first real import - in that order, listed there.

Version 1 is done when the planner can, on her phone: enter a new meal, plan next week, see what it
costs, take the shopping list to Costco and Woolworths, and import both receipts afterwards. **In a browser on a
phone-sized screen it can (2026-10-22); on her iPhone, through the add-on on the Pi, it waits on the owner's checks.** When
they pass, fold this doc: its decisions table and "Out of version 1" into a `docs/modules/` overview, the rest to `archive/`.
